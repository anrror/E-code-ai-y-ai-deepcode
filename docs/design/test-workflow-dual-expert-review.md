# test-workflow Skill 双视角评审

**方法**：分别以高级测试专家、高级技术专家的立场审视，每个结论都有可复现的实测证据。递进进行，每轮深入上一轮未解释清楚的地方。

**数据时效**：文中测试数（27）与行数（134）为本轮评审时的快照。此后：产品决策轮 34 个测试；basis 层升级后 47 个测试、9 个脚本。

---

# 第一部分：高级测试专家视角

## 第一轮：这份报告能不能用来做发布决策？

### 实测：不能

构造一个场景——5 个 critical 用例，只跑了 1 个：

```
用例总数: 5, 有闸门记录: 1
结论: SHIP
```

**4 个 critical 用例从未运行，报告说可以发布。**

这是本次评审发现的最严重缺陷，性质是**假阴性**：报告把"没测"当成"没问题"。

### 为什么会出现

`derive_verdict` 的所有规则都基于**已有数据**：

```python
if stats.open_critical > 0: ...      # 有数据才触发
if stats.gate_fail > 0: ...          # 有数据才触发
return "ship", ...                   # 默认落在 ship
```

**没有数据不触发任何规则，于是落到默认的 ship。**

这是个系统性思维错误：把"没有失败"等同于"通过"。

### 已修复

新增两条规则（优先级最高）：

```python
if stats.never_run_critical:   → hold    # critical/high 未运行
if stats.never_run:            → ship_with_conditions  # 其余未运行
```

实测修复后：

```
5 个 critical，只跑 1 个 -> hold
  4 active high/critical case(s) were never run: c1, c2, c3 (+1 more)
```

报告 §6 也新增了 `**never run** (4): c1, c2, c3` 明示。

## 第二轮：那"运行过"就等于"验证过"吗？

### 追问：用例数量是否等于覆盖数量？

实测：3 个 case_id 指向同一个测试函数：

```
重复实现组: {'tests/test_same.py::test_one': ['dup0', 'dup1', 'dup2']}
```

**报告原本不提示**。这意味着"20 个用例"可能只对应 8 个真实测试——**用例数量虚高**。

### 测试专家的实际担忧

在真实工作中，这个缺陷的后果是：

| 场景 | 表面 | 实际 |
|---|---|---|
| 为了凑覆盖率，同一测试换个 case_id 注册 3 次 | 覆盖率 100% | 真实覆盖率 33% |
| 参数化测试被拆成 5 个 case_id | 5 个用例 | 1 个测试函数 |

### 已修复

`collect` 现在按 `implementation.path` 分组，重复组写入报告 §6：

```
- **duplicate implementations** (one test function, several cases):
  - `tests/test_same.py::test_one` ← dup0, dup1, dup2
  The case count overstates what is actually protected.
```

---

## 第三轮：闸门的统计学意义是否被说清？

### 发现：闸2 的盲区从未被量化

闸2 判据：连跑 N 次全过。

| N | 真实 flake 率 10% 时，全过概率 |
|---|---|
| 3 | **72.9%** |
| 5 | 59.0% |
| 10 | 34.9% |

**3 次全过仍有 27% 概率放过一个 flake 率 10% 的用例。**

这个数字在文档中完全没出现。测试专家会立刻追问："那你这道闸到底拦住了什么？"

### 已修复

`references/gates.md` 新增「闸2 的统计局限」段落，明确：

- 这不是缺陷，是统计事实
- 关键路径用 N=10
- flake 治理不能只靠闸2，还要靠历史失败率

---

## 第四轮：变异闸门「杀死数 > 0」够吗？

### 发现：门槛形同虚设

实测数据（`core/team_context/integrations.py`）：

```
killed 72/192 = 37.5%
```

按 `> 0` 的判据，**杀死 1 个就通过**。这意味着：

- 一个只有 1 行断言的测试，如果恰好杀死 1 个变异，就算"合格"
- 37.5% 和 0.5% 在闸门看来没有区别

### 已修复

新增可配置门槛 `gates.mutation_min_kill_rate`，并**始终在报告中显示杀死率**：

```
killed 72/192 mutants (38%)
```

即使门槛设为 0，杀死率也可见——不再是一个被隐藏的数字。

---

## 第五轮：修复后的失败能否被正确解读？

### 追问：同一用例失败后又通过，算什么？

实测：

```
用例 A: fail -> pass（修复后重跑）
结论: ship_with_conditions
gate_pass=1 gate_fail=1
```

### 测试专家的判断：这是**误报**

失败后修复通过，应该视为**最终通过**，而不是"有失败"。

但当前实现把每次运行独立计数，导致：

| 情况 | 当前结论 | 应有结论 |
|---|---|---|
| 用例失败 → 修复 → 重跑通过 | ship_with_conditions | ship（若修复有记录） |
| 用例通过 → 回归失败 | ship_with_conditions | ship_with_conditions ✓ |

### 未修复（诚实记录）

**这个问题我没有修**，原因是修复需要先回答一个设计问题：

> "修复后重跑通过"是否需要"谁修的、何时修的"的记录？

如果不需要记录，那任何人都可以重跑掩盖问题。
如果需要记录，那这个机制与 `re-baseline` 的人确认流程重叠。

**当前状态**：报告显示 `gate_fail=1, gate_pass=1`，读者能看出有失败记录。这不算错，但不够。

# 第二部分：高级技术专家视角

## 第一轮：并发安全吗？

### 实测：不安全

三个线程各写 50 行：

```
期望 150 行，实际 149 行
LOST WRITES: 并发 append 丢数据
```

### 根因

`append_jsonl` 用普通 `open("a")` 追加。在 Windows 上，两个进程同时打开同一文件追加时，各自的写入位置独立计算——后写者覆盖前写者的字节。

**丢失率约 0.7%（1/150），但这是随机的**。在其他负载下可能更高。

### 这个缺陷在真实场景中的后果

方案明确支持多个场景同时运行：
- 多个 worktree
- 多个 agent 并行

如果两个 agent 同时跑闸门，`gates.jsonl` 会丢数据——**报告基于不完整的证据**。

### 已修复

`append_jsonl` 现在用文件锁（`msvcrt.locking` / `fcntl.flock`）：

```
期望 150，实际 150 -> OK
```

同时加了 `fsync`，保证进程崩溃时数据已落盘。

---

## 第二轮：写文件的原子性是否完整？

### 检查 `write_yaml`

```python
tmp = path.with_name(f"{path.name}.tmp-{os.getpid()}")
tmp.write_text(payload, encoding="utf-8", newline="\n")
tmp.replace(path)
```

**基本正确**：临时文件 + 原子替换。

### 但有两个瑕疵

| 瑕疵 | 后果 |
|---|---|
| 临时文件名用 `getpid()` | 同一进程的两次并发写会用同一临时文件 → 互相覆盖 |
| 没有 `fsync` | 崩溃时可能留下空的临时文件 |

### 未修复（记录理由）

`write_yaml` 目前只被用于**低频写入**（用例资产、审核记录），并发概率极低。

真正的并发风险在 `append_jsonl`（高频事件流），**那个已经修了**。

如果将来 `write_yaml` 用于高频场景，需要用 `uuid` 而非 `pid`，并加 fsync。

## 第三轮：错误处理是否可靠？

### 实测：部分场景会崩溃

```python
def load_config(state):
    if not path.exists():
        raise StateError(...)   # 有处理
    data = yaml.safe_load(...) or {}
    if not isinstance(data, dict):
        raise StateError(...)   # 有处理
```

`StateError` 在 `test_report.main` 里被捕获并返回 2。

### 但其他脚本没有捕获

检查 9 个脚本（新增 basis.py）的 `main`：

| 脚本 | 捕获 StateError |
|---|---|
| `test_report.py` | ✅ |
| `testflow.py` | ❌ 直接 `raise SystemExit` |
| `gate_check.py` | ❌ |
| 其余 5 个 | ❌ |

**后果**：配置错误时，用户看到 Python traceback 而不是可读的错误信息。

### 未修复（记录）

严重度低（错误信息仍可见），且修复涉及统一 8 个脚本的错误处理——工作量与收益不匹配。

**记录为已知问题**。

## 第四轮：性能是否可接受？

### 实测

| 操作 | 100 个用例 |
|---|---|
| `testflow status` | 562ms |
| `test_report --verdict-only` | 510ms |

### 分析

500ms 中：
- Python 启动 ~150ms
- 扫描 cases 目录 + 解析 100 个 YAML ~300ms
- 读取 JSONL ~50ms

**对 CLI 工具可接受**，但如果要在 CI 里每次提交跑，500ms × 几百次会累积。

### 优化机会

`status` 只需要计数，但 `read_records` 解析了完整的 YAML。可以用 `yaml.safe_load` 的轻量替代，或缓存。

**未优化**：100 个用例 562ms 不构成瓶颈，提前优化是浪费。

## 第五轮：依赖是否可控？

### 检查

| 依赖 | 用途 | 是否必需 |
|---|---|---|
| `PyYAML` | YAML 读写 | **必需** |
| `cosmic-ray` | 变异测试（Windows） | 可选（闸3 降级） |
| `mutmut` | 变异测试（Linux） | 可选 |
| `psutil` | 无 | 未使用 |

**PyYAML 是硬依赖**，脚本在缺失时给出明确提示：

```
PyYAML is required: pip install pyyaml
```

但 **`core.py` 的 `require_yaml()` 抛的是 `StateError`**，而 `StateError` 的定义在 `core.py` 里——如果 PyYAML 缺失，import 本身会失败吗？

实测：`core.py` 用 `try/except ImportError` 包裹，`yaml = None`，所以 import 成功。这点正确。

# 第三部分：两个视角的交集

## 三个被两个视角同时指出的问题

| 问题 | 测试视角 | 技术视角 |
|---|---|---|
| 未运行用例报 SHIP | 发布决策错误 | 缺"未运行"状态建模 |
| 重复实现 | 覆盖率虚高 | 缺唯一性约束 |
| 变异门槛 | 统计上无意义 | 配置项未落地 |

## 一条共同的根因

**三个问题都是"缺失的状态"**：

- 用例状态缺 `never_run`
- 实现路径缺唯一性
- 闸门结果缺 `kill_rate`

**共同点**：它们都是"没有记录某件事"，而不是"记录错了"。

这与前面几轮分析的结论一致：**静默丢失比错误更危险**，因为错误会被发现，丢失不会。

# 一句话总结

**测试专家关心「这个结论能不能信」，技术专家关心「这个系统会不会坏」。**

本轮评审中，两个视角各自独立地找到了对方可能忽略的问题：
- 测试专家发现「报 SHIP 但 4 个 critical 用例没跑」——技术专家不会想到去查这个
- 技术专家发现「并发写丢数据」——测试专家的场景里不会有并发

但它们指向同一个根因：**缺少状态建模**。而缺失的状态，永远不会在报告里出现。
