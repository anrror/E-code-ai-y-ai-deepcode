# 证伪实验结果（方案 §9 验证）

**目的**：验证方案 §9 的核心假设——「补写的测试能否抓住已修复的真实 bug」
**数据时效**：本文的 11 个测试为当时快照；该文件现为 14 个测试（后续追加 PEM 创建模式、跨进程稳定、dot 段转义）。


---

## 零、先记录一次方法论错误

**首次实验得出了错误结论**「现有测试完全抓不住缺陷」。

**错误原因**：用 `git stash push -- <文件>` 回退代码。但 `15e7ec22` 是历史提交，HEAD（`32cd7521`）已包含该修复——`git stash` 恢复的是 **HEAD 版本（已修复）**，不是修复前版本。因此测试自然全过，我误判为「测试无效」。

**这正是方案 §9.3 警告的「实验污染」**：实验条件没被真正建立，却得出了看似有力的结论。

**正确方法**：`git checkout <fix提交>^ -- <文件>`。

本报告只记录**修正后**的正确结果。

---

## 一、实验设计

1. 取真实 `fix(...)` 提交 `15e7ec22`（Jenkins/K8s 安全加固）
2. `git checkout 15e7ec22^ -- <两个服务文件>` 恢复到修复前
3. 用新补的测试跑（测试保留，代码回退）
4. 观察哪些测试失败——失败 = 抓住该缺陷

---

## 二、结果

**代码回退到修复前 + 11 个新测试**：

```
5 failed, 6 passed
```

失败的 5 个测试，逐一对应 `15e7ec22` 修复的 5 个缺陷：

| 失败测试 | 对应缺陷 | 修复前的真实危险 |
|---|---|---|
| `test_pick_raises_when_the_named_entry_is_missing` | `_pick` 静默回退到 `items[0]` | **配置写错 context 名 → 操作错误的集群** |
| `test_segment_escapes_path_separators` | 无 `_seg`，路径参数未转义 | namespace/pod 名可注入路径 |
| `test_segment_escapes_dot_segments` | 同上（`..` 被 HTTP 客户端规范化掉） | 路径穿越 |
| `test_unreadable_token_file_raises_integration_error` | `tokenFile` 读取裸抛 OSError | 用户看到原始异常而非可操作提示 |
| `test_crumb_returns_empty_on_a_non_json_response` | `response.json()` 未捕获 ValueError | 反代返回 HTML 时崩溃，构建发不出去 |

**通过的 6 个**是配置读写类断言，修复前后都成立——正确，它们测的是修复没破坏的既有行为。

### 2.1 换回修复后代码

```
11 passed
```

**结论：这 11 个测试锁定了 `15e7ec22` 的全部 5 个修复点。**

---

## 三、结果说明了什么

### 3.1 补测试是有效的

修复前代码：5 个失败。修复后代码：11 个全过。**证明补写的测试真实具备回归保护能力**，不是「通过但无效」。

### 3.2 它同时暴露了原来的空白

`15e7ec22` 在本会话早期提交，当时**没有任何测试覆盖这 5 个行为**（`test_integrations.py` 只测配置读写与掩码）。

| 时间点 | 缺陷状态 | 测试保护 |
|---|---|---|
| 修复前 | 5 个安全缺陷存在 | 0 |
| 修复后（当时） | 5 个已修复 | **仍然 0** |
| 现在 | 已修复 | 11 个（5 个是真正的守卫） |

**这个时间差持续了整个会话**——中途若有人重构 `k8s_service.py`，5 个缺陷会无声回归。

### 3.3 覆盖账本的必要性被实证

若有覆盖账本，`15e7ec22` 应产生 5 条 `added` 记录。现在没有——所以**没人能回答「这次修复之后哪些行为被保护了」**，答案当时是零。

| 假设 | 实验结果 | 判定 |
|---|---|---|
| 补写的测试能抓住真实 bug | 5/5 缺陷被抓 | ✅ **成立** |
| 现有测试覆盖不足 | 5 个修复当时零覆盖 | ✅ 成立 |
| 覆盖账本能发现缺口 | 无账本无法回答「保护了什么」 | ✅ 价值成立 |
| 从 diff 反向提炼契约 | 提炼出 6 条契约 | ✅ 成立 |
| 三道闸可执行 | 编译 PASS / 3/3 稳定 PASS / 变异 72/192 杀死 PASS | ✅ 实测通过 |
| 安全阀生效 | `auto_ai` 无变异工具时退出码 2 | ✅ 实测通过 |

### 4.1 实验方法的强制要求（补进方案 §9.2）

```
1. 选 N 个真实 fix 提交
2. 对每个：git checkout <commit>^ -- <affected files>   ← 不能用 git stash
3. 跑测试，记录哪些失败
4. git checkout HEAD -- <files> 恢复
5. 统计：能抓住的缺陷数 / 总缺陷数
```

**禁止用 `git stash`**：它恢复 HEAD 版本。若被测修复已在 HEAD 中，实验条件根本没建立，会得出「测试无效」的假阴性——这个错误会让人错误地放弃一个有效方案。

**有意思的是 `e327375e` 的证伪细节**：初版测试在旧代码下 4/5 通过——因为「内容正确」这个断言对 `write_text` 也成立。只有断言「写入路径经过临时文件 + `os.replace` + `0600` 创建」的测试才真正区分新旧实现。

**这是本次实验最有价值的教训**：断言"结果正确"往往抓不住"实现方式"的缺陷。原子性、权限窗口这类缺陷，必须断言**过程**而非**结果**。

`e41de2c5`（MCP SDK 延迟导入）是行为变化而非缺陷修复，无回归保护需求。

### 6.3 顺带发现的新缺陷（已修）

写测试时发现 `_seg("..")` 返回 `".."`：`urllib.parse.quote` 不转义点号，而 `..` 会被 HTTP 客户端规范化掉——**修复本身有残留缺口**。已补：

```python
def _seg(value: str) -> str:
    text = str(value)
    if text in (".", ".."):
        return text.replace(".", "%2E")
    return quote(text, safe="")
```

**这个缺陷是写测试时才发现的**——正是方案主张「补测试优先于批量生成」的又一证据。

## 八、总结

**方案的核心机制全部有实证支撑**，且实验过程本身发现了一个方案未预见的缺陷（`_seg("..")`）。

**最重要的结论**：

> 修复了 5 个安全缺陷，但当时零测试保护——这个空白持续了整个会话。
> 补测试的收益不是「提高覆盖率」，而是「让已修复的缺陷不会无声回归」。

这也是为什么方案的 §6.2 把「历史缺陷回补」放在「AI 批量生成」之前。
