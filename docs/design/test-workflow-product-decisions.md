# 产品决策：test-workflow Skill 的取舍

**决策者视角**：不追求技术完美，追求「这套东西能不能被真实团队用起来，并且不害人」。

**数据时效**：决策执行后实测 34 个测试、最长函数 144 行（`_run_mutation_cosmic_ray`）、仓库内 275 个测试文件。

---

## 一、决策框架

产品决策与技术决策的区别在于：**技术决策问「能不能做得更好」，产品决策问「值不值得做，不做会怎样」**。

三个判据，按优先级：

| 判据 | 问题 | 权重 |
|---|---|---|
| **安全** | 不做会不会害人（错误放行 / 掩盖问题） | 最高 |
| **可用** | 不做会不会没人用（摩擦太大 / 看不懂） | 高 |
| **成本** | 做的成本 vs 收益 | 中 |

**一条硬规则**：任何导致「错误放行」的缺陷，无论成本多高都必须修。

---

## 二、逐项决策

### 决策 1：「失败后通过」是否计为失败

**问题**：用例 A 首次失败，修复后重跑通过。当前报告仍计入 1 次 `gate_fail`，结论变 `ship_with_conditions`。

#### 三个选项

| 选项 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| A | 只认最新结果 | 修复后不再误报 | **任何人都能重跑掩盖问题** |
| B | 需要修复确认记录才认通过 | 防止掩盖 | 增加流程摩擦，可能让人不去修 |
| C | 保持现状（计入失败） | 保守，不放过 | 修复后仍显示有失败，误导 |

#### 决策：**选 A，但加一条约束**

**理由**：

1. **选项 B 的摩擦太大**。要让「谁修的、何时修的」入账，等于给每次失败修复加一道审批。现实结果是：测试员不会去记录，而是直接重跑然后忽略报告里的失败——**问题从"有记录"变成"有记录但没人看"**，更糟。

2. **选项 C 会造成误报疲劳**。如果修复后仍显示红，人会开始忽略所有红色标记——这是最危险的结局，比误判单个用例严重得多。

3. **选项 A 的风险可以用一条约束控制**：只认最新结果，但**报告必须同时显示历史**（"此用例共运行 3 次，其中 1 次失败"）。这样：
   - 正常修复 → 结论不再红
   - 想掩盖 → 历史记录仍在，有经验的人能看出来

#### 具体实现

```
最新结果决定结论
历史结果写入报告（§5 闸门明细已含每次运行）
新增告警：同一用例失败后又通过，且失败与通过间隔 < 1 小时，标记为「快速重跑」
```

**判据**：如果失败后 1 小时内就通过，可能是环境抖动或重跑，而非真实修复。这不是禁止，是提示。

**为什么用 1 小时**：真实修复需要改代码、提审、合并、CI——不可能在 1 小时内完成。1 小时内的通过几乎必然是"重跑碰巧过了"。

---

### 决策 2：`write_yaml` 用 pid 命名临时文件

**问题**：同一进程并发写会互相覆盖。

#### 决策：**修，但用最低成本方案**

**理由**：修复成本极低（把 `getpid()` 换成 `uuid4()`），而不修的理由（"低频写入"）无法验证——我不知道未来谁会怎么用它。

**产品原则**：低成本的隐患就修掉，不要赌"不会发生"。

---

### 决策 3：7/8 脚本不捕获 StateError

**问题**：配置错误时用户看到 Python traceback。

#### 决策：**不修，但补一句话**

**理由**：

1. 这是 CLI 工具，用户是开发者。**traceback 对开发者是有用信息**，不是障碍。
2. 美化错误信息的收益（更好的体验）远小于成本（8 个脚本统一改造 + 测试）。
3. **但需要明确说出来**：在 SKILL.md 里写清楚"配置错误会看到 traceback，这是预期行为，看最后一行的 StateError 信息"。

**产品决策的关键**：不是修所有问题，而是**让已知的不完美变成预期行为**。

---

### 决策 4：500ms 启动开销

#### 决策：**不优化**

**理由**：500ms 是 CLI 的合理范围（git status 也要 50-100ms，npm 要 300ms+）。优化到 200ms 的收益不足以抵消改动的风险。

**但如果**将来要在 CI 里每次提交跑，那需要的是另一种架构（常驻服务或增量缓存），而不是优化单次启动。**现在优化是在错误的维度上努力。**

---

### 决策 5：`_run_mutation_cosmic_ray` 134 行

#### 决策：**不拆**

**理由**：这个函数的问题是"做了三件事"（写配置、跑子进程、解析结果）。但拆开之后：

- 写配置需要一个路径参数
- 跑子进程需要配置路径 + 会话路径
- 解析需要输出 + 配置

**拆完后是三个函数互相传递 5 个参数**——这不是更清晰，是更分散。

**产品判断**：函数的可读性不等于行数少。134 行但有清晰的三段注释，比 3 个 40 行的函数各自接收一堆参数更好读。

---

### 决策 6：`classify` 75 行不拆

#### 决策：**不拆**（这条最重要）

**理由**：**判定顺序本身就是业务逻辑**。

```
1. 环境问题？   → 是则返回
2. 不稳定 + 有独立证据？ → flaky
3. 不稳定但无证据？      → unknown
4. 测试缺陷？
5. 否则 → real
```

拆成 `_is_environment()` / `_is_flaky()` / `_is_test_defect()` 后，**顺序关系会丢失**——调用方可以按任意顺序调用，而顺序错了结果就错了（先判 flaky 会把环境问题误判）。

**产品判断**：这里"难读"是必要的复杂度，因为它保护的是一个容易出错的顺序。

---

### 决策 7：是否需要「测试目标覆盖」度量

**问题**：现在有契约覆盖率、功能触达，但没有"业务目标覆盖"。

#### 决策：**不加**

**理由**：这是**过度设计的典型**。

「业务目标」在真实团队里无法自动度量——它需要人判断"这个需求的目标达成了吗"。加一个自动计算的"目标覆盖率"只会制造虚假的确定性。

**已经有的是够的**：
- 需求覆盖清单（§2）→ 每条需求有无用例
- 功能触达（§4）→ 每个模块有无用例
- GAP 标记 → 需求有用例但全失效

**产品判断**：度量越少越可信。多一个指标，就多一个可以造假的地方。

---

### 决策 8：是否强制「用例必须挂在需求上」

**现状**：无需求锚点的用例只触发 `ship_with_conditions`（若是 critical/high）。

#### 决策：**保持现状，不升级为强制**

**理由**：

强制（拒绝无锚点用例入库）会导致：
1. 存量用例无法纳管（272 个测试文件大多无需求引用）
2. 新用例为了过闸，随便填一个 `requirement_ref` 凑数——**比不填更糟**，因为假锚点让 GAP 检测失效

**现状的软约束更有效**：报告里显示"3 个 high 用例无需求锚点"，压力来自可见性，而不是闸门。

**产品判断**：**可见性比强制性更有效**。强制会被绕过，可见会被看见。

## 三、决策后的行动清单

### 立即执行（本轮）

| # | 行动 | 理由 |
|---|---|---|
| 1 | 报告结论只认最新结果，同时显示运行历史 | 消除误报疲劳（最危险） |
| 2 | 快速重跑（<1h）标记提示 | 低成本防止掩盖 |
| 3 | `write_yaml` 改用 uuid 命名 | 低成本消除隐患 |
| 4 | SKILL.md 说明 traceback 是预期行为 | 把不完美变成预期 |

### 明确不做（并说明理由）

| # | 不做 | 理由 |
|---|---|---|
| 5 | 8 个脚本统一错误处理 | 收益 < 成本，已用文档说明 |

| 7 | 拆 `_run_mutation_cosmic_ray` | 拆完更分散 |

## 四、产品视角的核心判断

### 这份 Skill 的定位

**它不是"让测试变好"的工具，而是"让测试的结论可信"的工具。**

这个定位决定了所有取舍：

| 如果目标是"让测试变好" | 如果目标是"让结论可信" |
|---|---|
| 应该加更多检查 | 应该删掉不可信的检查 |
| 应该强制流程 | 应该让问题可见 |
| 应该提高覆盖率指标 | 应该减少指标数量 |
| 追求自动化率 | 追求结论的可靠性 |

**本 Skill 选的是后者。**

### 一条贯穿所有决策的原则

> **宁可显示"不知道"，也不要显示"没问题"。**

这条原则解释了：
- 为什么 `unknown` 独立成类而不是并入噪音
- 为什么空状态给 `hold` 而不是 `ship`
- 为什么未运行的 critical 用例给 `hold`
- 为什么阻塞闸门不算失败但也不算通过

**所有决策都能追溯到这一条。**

### 最大的产品风险

**不是技术缺陷，是没人用。**

如果测试组试一次就放弃，前面所有设计归零。所以：

| 风险 | 对策 |
|---|---|
| 可测性评审太费时（15-30 分钟） | 需要观察真实耗时，超过 40 分钟就要简化 |
| 报告太长（12 段） | 第一段是结论，后面是证据——可以只看第一段 |
| 契约写不出来 | 阶段 0 的产出物必须能自然导出契约 |

**这三个风险都不是代码能解决的，需要真实使用反馈。**
