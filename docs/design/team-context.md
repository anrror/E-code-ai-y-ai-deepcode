# 团队上下文平台：设计与界面方案

> 状态：设计稿（待确认）
> 范围：DeepCode 的团队级上下文子系统的领域模型、规则、信息架构、界面与落地分期
> 关系：实现《团队级 AI 编码上下文管理平台设计文档》（下称"原文档"）中仓库侧与知识侧的核心，外部系统（Confluence/GitBook、CodeGraph、MCP Aggregator）作为对接点

---

## 0. 现状与问题

已落地（后端）：

- 六层实体（org/line/product/project/batch/version/task）、单主归属、可选层；
- 知识条目 schema（scope/type/statement/rationale/evidence/confidence/status/owner/source/supersedes）；
- 装配：主链由近及远、红线不可覆盖、评审优先、外部标注、引用产品（PaaS/标准/历史）一跳到装配；
- 提示词注入与 `team_context` 工具（assemble/search/add）。

当前界面原型的问题（必须替换）：

1. **只是一个 YAML 文本编辑器**：没有结构化表单，用户要记字段名与层级规则；
2. **依赖已存在的会话**：通过 `file/*` RPC 读写，项目没有会话时无法配置；
3. **没有装配预览**：用户看不到"Agent 实际会读到什么"、每条来自哪一层、预算占用；
4. **没有评审闭环**：草稿、评审、例外登记只在文件里体现；
5. **没有全局视角**：看不到组织树、未配置层、外部/历史资产的全貌。

---

## 1. 设计目标与非目标

目标：

1. 用**树 + 详情**的界面，让非工程角色也能配置六层上下文；
2. 每条规则"所见即所得"：改完立刻能看到装配结果与贡献来源；
3. 把治理动作（评审、例外、外部确认）变成界面里的显式操作；
4. 配置是**项目级**的，不依赖任何会话；
5. 桌面端与 Web 端共用同一套页面组件。

非目标：

- 不做 Confluence/GitBook 的替代品；只做导入/导出与引用；
- 不做 CodeGraph 索引本身的实现；只做"索引位置"的登记与工具接入；
- 不做多租户 SaaS 的组织管理（角色/审批流先以"只读/可写"与评审状态表达）。

## 2. 概念模型

### 2.1 管理链与资产

```text
org（公司/子公司）
└── line（产线）
    ├── product（标准产品，可多个）
    ├── product（历史产品，archived）
    └── project（项目）──┬── batch（批次）
                         │     └── version（版本）
                         │           └── task（任务）
                         └── references → product / 其他产线能力
org 也可直接拥有 product（PaaS 产品）
```

- **管理链**决定继承顺序：task → version → batch → project → line → org。
- **product 是资产，不是第七层**：它不参与任何项目的父链，项目通过 `references` 引用；引用**不覆盖**项目自身规则。
- **同一实体只有一个主归属**；跨线复用一律引用，不复制。
- **每一层都可配可不配**：未配置的层不贡献内容，已配置的祖先照常生效；`parent` 指向未配置层时链路在此结束。

### 2.2 实体字段

| 字段 | 说明 | 适用 |
|---|---|---|
| `id` | `kind://slug`，默认由目录名推导 | 全部 |
| `name` | 展示名 | 全部 |
| `parent` | 主归属父级（kind 受限） | line/product/project/batch/version/task |
| `external` | 外部团队维护，只读镜像 | batch / product |
| `archived` | 历史资产，可检索、带 `[historical]` 标注、非当前标准 | product |
| `workspace` | 绑定本地目录（task 用） | task |
| `references` | 引用的产品/能力，一跳 | project / product |
| `designs` | 设计文档路径（指针，不是正文） | product / project |
| `codebases` | 代码库路径或 URL（指针） | product / project |

### 2.3 知识条目

沿用原文档 schema：`scope`、`type`（redline/decision/convention/domain/design/lesson/external）、`statement`、`rationale`、`evidence`、`confidence`、`status`（draft/reviewed/deprecated）、`owner`、`source`、`valid_from/to`、`supersedes`。

---

## 3. 规则（装配语义）

1. 由近及远读取主链；
2. 公司级 `redline` 永不被下层覆盖；下层若用 `supersedes` 指向红线，该条被拒绝并在预览里标红；
3. `reviewed` 优先于 `draft`，`deprecated` 剔除；
4. 外部批次/外部产品的条目标注"未验证"，默认不作为团队事实（可关闭包含）；
5. 引用产品的内容排在主链之后，标注 `referenced: <id>`；历史产品再加 `[historical]`；
6. 输出受预算约束，先裁剪最弱条目（外部 > 草稿 > 低置信）；
7. 层内 `AGENTS.md` 由远及近注入，最近一层最后出现（覆盖语义）。

## 4. 信息架构（IA）

新增一级目的地 **Team**（侧栏与 Automations / Skills / MCP 同级），内部五个视图：

```text
Team
├── 1. 组织树（Explorer）        左栏，常驻
├── 2. 层详情（Detail）          中栏，随选中节点切换
│     ├── 概览（字段 + 状态）
│     ├── 知识（表格 + 评审操作）
│     ├── 指令（AGENTS.md 编辑器）
│     └── 高级（YAML）
├── 3. 装配预览（Preview）       右栏抽屉 / 独立 Tab
├── 4. 评审队列（Review）        顶部入口，跨层待评审草稿
└── 5. 产品库（Products）        独立页面：PaaS / 标准 / 历史产品与维护团队
```

项目打开后的工作区另有一个 **代码（Code）** 视图（不放在 Team 下，见 5.6）：浏览该项目的代码与文件。

**为什么是树 + 详情**：六层是强层级，树能一次展示"配了什么、没配什么、哪些是外部/历史"；详情区避免在弹窗里编辑长表单。装配预览常驻可切换，解决"改完不知道 Agent 看到什么"。

## 5. 页面设计

### 5.1 组织树（左栏）

```text
┌ Team ──────────────────────────────┐
│ [本项目] [共享(本机)]      + 新建 ▾ │  ← 作用域切换
│ 🔍 搜索层/条目…                     │
│                                    │
│ ▾ org://auto-sub        3 条        │
│   ▾ line://auto-outsourcing  5 条   │
│     ▸ product://paas      2 条  ⬡外部│
│     ▾ product://std-crm   4 条      │
│     ▾ product://legacy-crm 1 条  ◷历史│
│     ▾ project://changan   6 条      │
│       ▾ batch://phase-1   2 条      │
│         ▾ version://v1.2.0 1 条     │
│           ▾ task://LEAD-1234 2 条 ● │
│     ＋ 未配置：batch/version…        │  ← 可选层占位
│                                    │
│ 引用：project://changan → ⬡paas ⬡std │
└────────────────────────────────────┘
```

要点：

- 节点右侧显示本层知识条数与**状态徽标**（外部/历史/草稿数）；
- 未配置层以浅色"＋ 配置"占位出现在应有位置，点开即为该层建目录；
- product 下不挂 project（资产与交付分离）；project 行下方显示它引用的 product chips；
- 搜索同时搜层名、条目正文；命中条目直接跳到详情并高亮。

### 5.2 层详情

顶部：`org://auto-sub` · 3 条知识 · 已评审 2 / 草稿 1 · [装配预览] [⋯]

四个 Tab：

**A. 概览**

```text
名称        [ Auto Sub            ]
类型        org（不可改）
上级        无（org 为根）
绑定目录    —                          [选择文件夹]   ← 仅 task
引用        [＋ 添加产品引用]  ⬡product://paas ✕
设计        [＋ 路径] docs/paas/design.md ✕
代码库      [＋ 路径/URL] https://git/paas ✕
状态        ☐ 外部  ☐ 历史（archived）
[保存]
```

- 上级选择器只列出**合法父级类型**（如 project 只能选 line）；
- 类型由目录决定，创建后不可改（改类型 = 新建 + 迁移，界面提供"迁移"而不是直接改）；
- 必填校验就地提示（slug 非法、父级不存在、引用成环）。

**B. 知识**

```text
筛选：[全部类型▾] [全部状态▾] [全部置信▾] [来源▾]      + 添加条目
┌──────────────────────────────────────────────────────────────┐
│ 类型     陈述                         置信  状态     操作      │
│ 红线🔒   禁止将生产密钥写入仓库        高    已评审   —         │
│ 决策     线索中心使用 PostgreSQL       高    已评审   [编辑]    │
│ 教训     导入器失败前重试两次          中    草稿     [评审][编辑]│
└──────────────────────────────────────────────────────────────┘
右侧抽屉：分栏编辑（陈述/理由/证据/置信/来源/有效期/替代），实时校验
```

- 红线条目锁定编辑（仅组织管理员可见"解除"入口，需二次确认）；
- 草稿行内出现"评审通过 / 退回"按钮（治理动作显式化）；
- 外部来源条目显示"来源：外部二期 · 未验证"，并提供"发起确认"（提升为内部）。

**C. 指令（AGENTS.md）**

- 富文本不做，保持 Markdown 源码 + 预览切换；
- 顶部提示"这一层对下游可见；更近的层可覆盖同名规则"；
- 保存前展示"影响面"：有多少下游层会读到它。

**D. 高级（YAML）**

- 只读查看为主；可切"直接编辑"，保存前做 schema 校验，错误定位到行；
- 导入/导出整棵树（`.zip` 或单文件），用于与 Git / 公司知识库同步。

### 5.3 装配预览（关键页面）

```text
┌ 预览：task://LEAD-1234 ────────────────────────────────┐
│ 模式：[团队事实] [含外部参考]   预算 ▓▓▓▓▓▓░░░░ 62%     │
│ 链：task → version → batch → project → line → org       │
│ 引用：⬡paas ⬡std-crm ◷legacy-crm                        │
├─────────────────────────────────────────────────────────┤
│ 红线（公司级）                                          │
│  • 禁止将生产密钥写入仓库        来自 org://auto-sub     │
│ 团队事实                                                │
│  • 线索中心使用 PostgreSQL      来自 project://changan   │
│  • PaaS 调用统一走网关          来自 ⬡product://paas     │
│ 草稿                                                    │
│  • 导入器失败前重试两次          来自 task://LEAD-1234   │
│ 外部参考（未验证）                                      │
│  • 二期新增 GraphQL 端点         来自 batch://phase-2    │
│ 产品指针                                                │
│  • ⬡product://std-crm  codebases: …  designs: …        │
├─────────────────────────────────────────────────────────┤
│ 被拒绝的覆盖：task:// 的 K-9 试图覆盖公司红线  [查看原因] │

└─────────────────────────────────────────────────────────┘
```

- 每条知识后标注**贡献层**，可点击跳转；
- 顶部预算条实时反映裁剪，超出时列出"被裁掉的最弱条目"；
- "复制装配文本"给排查用；"在会话中验证"可直接开一个临时会话（可选）。

### 5.4 评审队列

- 跨层列出 `status=draft` 与外部待确认条目；
- 行内操作：通过 / 退回（填理由）/ 提升到父层（项目经验 → 产线资产）；
- 批量通过与批量退回；按层、类型、owner 过滤；
- 通过后该条进入 `reviewed`，装配预览即时变化。

### 5.5 产品库（独立页面）

产品库与组织树分开：组织树回答"谁在什么层级"，产品库回答"我们有哪些可复用资产、谁维护、当前是哪个版本"。

```text

│ [全部] [PaaS] [标准产品] [历史产品]   🔍 搜索        + 新建产品      │
│ 归属：[全部公司/产线▾]  状态：[已发布▾]  维护组：[▾]                 │
├────────────────────────────────────────────────────────────────────┤
│ 产品                    归属            维护组       最新版本  状态   │
│ ⬡ PaaS 网关              org://auto-sub 平台架构组  v2.3.0   已发布 │
│ ⬡ 标准 CRM               line://auto-out 产线维护组 v1.8.1   评审中 │
│ ◷ 历史 CRM（归档）        line://auto-out 产线维护组 v1.0.0   历史   │
├────────────────────────────────────────────────────────────────────┤
│ 选中：⬡ 标准 CRM                                                  │
│  维护组：产线维护组（3 人）   Owner：@zhang   [成员与角色]           │
│  版本：v1.8.1（评审中）→ 变更请求 CR-12：新增线索去重规范            │
│  设计：docs/standard-crm/design.md   代码库：https://git/std-crm    │
│  被引用：project://changan（3 处）、project://…                     │
│  [查看装配影响]  [发布新版本]  [发起变更请求]                        │
└────────────────────────────────────────────────────────────────────┘
```

#### 专职维护团队与生命周期

产品库不是"谁都能改"的目录，而是有明确维护者的资产库：

| 角色 | 权限 |
|---|---|
| 产品 Owner（每产品一人） | 发布/归档、指定评审人、合并变更请求 |
| 维护组成员 | 编辑草稿、提交评审、维护设计与代码库指针 |
| 评审人 | 通过/退回变更请求 |
| 使用方（项目成员） | **只读** + 发起变更请求（不能直接改已发布内容） |

生命周期：

```text
draft（草稿） → in-review（评审中） → published（已发布） → deprecated（弃用） → archived（历史）
```

- 只有 `published` 计入"当前标准"；`archived` 仍可被引用，但装配时带 `[historical]`；
- 已发布条目不可直接编辑，必须走**变更请求（CR）**：影响面（哪些项目引用、哪些知识依赖）→ 评审 → 发布新版本；
- 每次发布生成不可变版本号（`v1.8.1`），项目引用可"跟随最新"或"钉住版本"；
- 维护组的成员变更也要记录（谁在何时获得/失去权限）。

#### 与组织树的关系

- 产品的 `parent` 决定归属（公司或产线），组织树里仍显示产品节点；
- 产品库是同一数据的"资产视角"，提供维护团队、版本、变更请求与引用影响；
- 项目引用产品后，产品库反向显示"被哪些项目引用"，便于评估变更风险。

### 5.6 代码浏览（项目打开后）

打开项目后，工作区提供 **代码** 视图：不依赖会话，直接浏览该项目的文件。

```text
┌ 代码：com-cipher ───────────────────────────────────────────────────┐
│ 🔍 文件名/内容搜索            [刷新]   分支：main   ● 未提交 3        │
├──────────────┬─────────────────────────────────────────────────────┤
│ ▾ src/       │  1  import { createServer } from "node:http";        │
│   ▸ api/     │  2                                                   │
│   ▸ models/  │  3  export function start() {                        │
│   app.ts     │ …                                                   │
│ package.json │                                                     │
│ README.md    │                                                     │
└──────────────┴─────────────────────────────────────────────────────┘
```

要点：

- **只读**浏览；编辑仍走会话与权限门禁，避免"绕过 agent 直接改代码"；
- 大文件截断并标注（与现有 `file/read` 的上限一致），二进制/符号链接明确拒绝；
- 语法高亮按扩展名，未知类型退化为等宽文本；
- 点击文件可在"在会话中打开"（把路径作为引用加入输入框）；
- 与 Team 的 `codebases` 指针联动：从产品库点击代码库路径可直接打开该项目的代码视图。

接口：项目级 `project/files/list`、`project/files/read`（与现有 `file/*` 的会话级实现共用底层服务，仅把"工作区"从会话解析改为项目解析）。

## 6. 交互与状态

| 场景 | 设计 |
|---|---|
| 未配置层 | 树中占位"＋ 配置"，详情区显示该层示例与"从上层复制模板" |
| 缺失父级 | 不报错；概览显示"上级未配置，链路在此结束"并给"去配置上级" |
| 引用成环/自引用 | 保存前拦截，字段级错误提示 |
| 目录类型不匹配 | 树中显示为"孤立目录"，提供"修正类型/移动" |
| 红线上被覆盖 | 预览中"被拒绝的覆盖"区块，点击定位到该草稿 |
| 并发编辑冲突 | 保存冲突时提示"文件已被修改"，提供"对比/覆盖" |
| 未保存离开 | 统一未保存拦截（沿用现有 inspector 草稿确认） |
| 空状态 | 三类空状态：无 org 配置、项目未挂 task、全部未配置 |
| 键盘 | 树 ↑↓/←→、⌘S 保存、⌘K 搜索、⌘Enter 评审通过 |
| 可访问性 | 树用 `role=tree/treeitem`、焦点可见、徽标有文字替代 |

**不做**的事情（避免界面变复杂）：

- 不做拖拽改父级（层级由类型约束，移动等于迁移，走显式"迁移"流程）；
- 不在树里直接编辑（详情区统一编辑）；
- 不提供"一键清空"（危险操作走导入/导出与确认）。

## 7. 数据与 API

### 7.1 存储

- 仓库层（随代码提交）：`<workspace>/.deepcode/team/<kind>/<slug>/`，文件 `entity.yaml`、`knowledge.yaml`、`knowledge/*.yaml`、`AGENTS.md`；
- 共享层（本机）：`~/.deepcode/team/...`，用于公司/产线级内容；
- 界面顶部作用域切换决定写入哪一层；共享层默认只读，需显式解锁。

### 7.2 RPC（项目级，不依赖会话）

```text
team/tree        {projectId, scope}            → 层级树 + 未配置占位 + 计数/徽标
team/read        {projectId, scope, entityId}  → 实体 + 知识 + 指令 + 校验问题
team/upsert      {projectId, scope, entity}    → 创建/更新实体（含 rename/move 的显式迁移）
team/remove      {projectId, scope, entityId}  → 删除层目录（二次确认，级联提示）
team/knowledge/upsert  {projectId, scope, entry}
team/knowledge/remove  {projectId, scope, entryId}
team/knowledge/promote {projectId, scope, entryId, owner}
team/knowledge/confirm-external {…}            → 外部知识确认
team/preview     {projectId, taskId, includeExternal, maxChars} → 装配文本 + 贡献映射 + 裁剪明细
team/validate    {projectId, scope}            → 全树校验（父级/引用/环/类型）
team/import|export {projectId, scope, payload}
```

产品库与代码浏览：

```text
team/product/list          {owner?, status?, kind?}       → 维护组、最新版本、状态、被引用数
team/product/read          {productId}                    → 详情 + 版本 + 维护组 + 变更请求
team/product/publish       {productId, version, changelog}→ 发布不可变版本
team/product/change-request {productId, patch, reason}    → 使用方发起 CR
team/product/cr/review     {crId, decision, note}         → 评审通过/退回
team/product/members       {productId, role, action}      → 维护组成员变更
project/files/list         {projectId, path, depth, limit}
project/files/read         {projectId, path, maxBytes}
```

要点：`team/*` 与 `project/files/*` 都是**项目级**，因此配置与代码浏览都不依赖任何会话（修正原型缺陷）；共享层只读，写操作显式解锁并提示"修改将影响本机所有项目"。

## 8. 落地分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| P0 | 项目级 `team/*` API + 树/详情/预览只读；`project/files/*` 只读代码浏览 | 无会话也能看到完整树、装配结果与项目代码；外部/历史/未配置层可见 |
| P1 | 结构化编辑：实体表单、知识表格、AGENTS.md 编辑器；产品库只读（列表/详情/引用影响） | 不写 YAML 即可完成"建层—加知识—评审—预览"全流程 |
| P2 | 评审队列、提升/退回/例外登记、外部确认；产品变更请求/发布/维护组；导入导出 | 评审动作改变装配结果；外部条目未经确认不进入"团队事实"；产品发布走 CR |
| P3 | 共享层编辑权限、与公司知识库/CodeGraph/MCP 的对接、迁移向导 | 从知识库导入一批候选条目并完成评审 |

每期都必须通过的界面底线：

- 键盘可达、焦点可见、错误就地提示；
- 任何写操作都有确认或可撤销路径；
- 装配预览与真实注入使用同一个装配函数（不做第二套逻辑）。

## 10. 已确认决策

1. **入口**：Team 作为一级目的地（与 Automations / Skills / MCP 同级）。
2. **知识编辑**：结构化表单为主，YAML 作为高级模式（保存前校验）。
3. **共享层**：默认只读；解锁后才可编辑，并提示影响本机所有项目。
4. **评审**：需要状态流（draft / reviewed / deprecated），草稿通过评审才进入团队事实。
5. **产品**：独立产品库页面，配专职维护组（Owner / 维护成员 / 评审人 / 使用方只读）与版本、变更请求生命周期。
6. **代码浏览**：项目打开后只读展示代码，不依赖会话。
