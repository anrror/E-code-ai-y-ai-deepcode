# 多轮递进分析：从「表面可用」到「结构性缺陷」

**方法**：每一轮只回答上一轮暴露出的、尚未解释清楚的问题。每轮结论都有实测证据。

---

## 第一轮：这个方案到底保护了什么？

### 表面答案

三个机制：闸门（编译/稳定/变异）、契约资产化、覆盖账本。

### 追问：哪个环节真正提供了保护？

实测数据：

| 机制 | 实测证据 | 真实保护力 |
|---|---|---|
| 四道闸门 | 编译 PASS、3/3 稳定 PASS、变异 72/192 | **强**（变异确实抓住了 10/11 注入缺陷） |
| 契约资产化 | 3 个用例，需求锚点齐全 | **弱**（只是元数据，无强制力） |
| 覆盖账本 | 强制授权，拒绝无 ref 的退役 | **强**（唯一防静默流失的机制） |

### 第一轮结论

**真正的保护力来自两处：变异测试 + 覆盖账本。** 其余的（意图规范、评审档位、生命周期状态）是**流程脚手架**，它们不直接产生保护，只是让保护可被组织执行。

**这解释了为什么 `auto_ai` 必须拒绝无变异测试的组合** —— 一旦去掉变异，`auto_ai` 的唯一客观信号就没了，剩下全靠流程自律。

---

## 第二轮：既然保护力来自变异测试，那变异测试可信吗？

### 追问：我的 10/11 杀死率说明什么？

回到实测细节：

```
killed 10/11
SURVIVED: 去掉 chmod 0600（等价变异，合理）
```

但这里有个**未解释的问题**：我注入的是**我自己设计的变异**。这会系统性高估测试强度——我倾向于注入"我已经想到要测的东西"。

真正的变异测试（cosmic-ray）跑出了 **72/192 = 37.5%** 的杀死率。这个数字远低于 90%。

### 两个数字为什么不一致

| 指标 | 数值 | 含义 |
|---|---|---|
| 手工变异杀死率 | 91% | 针对**我关心的行为**，测试很严格 |
| cosmic-ray 全量杀死率 | 37.5% | 针对**模块所有可变异点**，覆盖不完整 |

**两者都真实，但回答不同问题**：
- 手工变异 = "我声称保护的契约，是否真被验证" ← 高
- 全量变异 = "这个模块的每个逻辑分支，是否都有测试" ← 低

### 第二轮结论

**方案的变异闸门（杀死数 > 0）门槛太低。** 72/192 = 37.5% 就会判 PASS，但意味着 62.5% 的逻辑变更不会被任何测试发现。

真实含义：**闸门只验证"至少有一个测试有效"，不验证"覆盖是否充分"。**

这是一个**未在设计文档中言明的边界**。`references/gates.md` 写的是「杀死变异体数 > 0」，这个标准几乎等于"有任何测试就行"。

**修正建议**：闸门应分级：

| 等级 | 判据 | 适用 |
|---|---|---|
| 最低 | 杀死数 > 0 | 新增用例的准入（防空断言） |
| 基线 | 杀死率 ≥ 模块当前基线 | 防新增用例拉低整体覆盖 |
| 目标 | 杀死率 ≥ 60% | 核心模块 |

## 第三轮：那个 37.5%，有多少是「不该被杀死」的？

### 追问：cosmic-ray 的 192 个变异里，哪些是可杀死的？

变异分三类：

| 类型 | 说明 | 能否被测试杀死 |
|---|---|---|
| **等价变异** | 不改变行为（如 `chmod` 冗余） | 不能，杀不死是对的 |
| **等价于未覆盖分支** | 改变的行为没有测试覆盖 | 能，但当前没测 |
| **不可达变异** | 变异的代码永远不执行 | 不能 |

**我从未测量过这三类的比例。** 所以 37.5% 这个数字**无法解释**——分母里混了多少"本来就杀不死"的。

### 关键计算

如果 192 个里有 30% 是等价变异，那真实可杀死数是 134，37.5% 应修正为 **53.7%**。

**这个修正会完全改变结论**：从"覆盖不完整"变成"覆盖尚可"。

### 第三轮结论

**我给出的 37.5% 是一个不可解释的数字。** 正确做法是：
1. 排除等价变异（需要人工判定，或用 cosmic-ray 的 `survived` 分类）
2. 只对"可杀死变异"计算杀死率

**方案层面**：闸门规则必须写明"杀死率的分母是什么"。否则这个数字可以被任意解释。

## 第四轮：为什么失败分类器会掩盖真实 bug？

### 第二轮/第三轮都在讲"测到了什么"，这一轮转向"测到之后怎么处理"

实测三个反例（全部复现）：

| 输入 | 输出 | 问题 |
|---|---|---|
| 断言内容提到 `ConnectionError` | `environment` | 被测系统正确返回它，测试断言它 |
| 同一断言错误，重跑 pass/fail/pass | `flaky` | 间歇性真实 bug（数据边界）被归类为噪声 |
| 并发锁 bug 偶发通过 | `flaky` | 永久掩盖 |

### 根因：分类器用「关键字 + 重跑」近似「因果归因」

真实世界里：
- **flaky** = 测试本身不稳定（同样的代码、同样的输入，行为不确定）
- **间歇性 bug** = **产品**在特定时序/数据下出错

两者在观测层面**完全一致**：都是"有时过有时不过"。

**分类器无法区分它们，因为区分需要理解"不确定性来自哪里"。**

### 这有多严重

方案里 `flaky` 的定义是"不进入归因"。所以：
- 真实的并发 bug → 判 flaky → **永不进入归因 → 永不修复**

这是**系统性掩盖**，不是偶发错误。

### 第四轮结论

失败分类器的设计**把"证据不足"当成了"排除嫌疑"**。

正确逻辑应该是：

```
无法确定 → unknown（仍需人看）
确定为 flaky → flaky（可排除）
```

而不是：

```
看起来像 flaky → flaky（排除）
```

**修正建议**：加入 `unknown` 类别，并规定「重跑结果不一致 **不能**单独作为 flaky 证据」——必须同时满足「同 revision 的历史失败率 > 阈值」或「已知的不确定源（时间/随机/网络）」。

## 第五轮：如果分类器不可靠，归因环节还成立吗？

### 追问：归因的输入是什么？

```
失败 → 三分类 → 只有 real 进入归因
```

如果分类器把真实 bug 误判为 flaky（第四轮证明会），那么**归因永远看不到它**。

### 这是级联失效

```
分类器误判 → 真实 bug 被排除 → 归因不触发 → 缺陷单不产生 → 永不修复
```

而方案对归因的所有防护（证据链、置信度、不自动提单）**都在这个问题之后**。防得再严，输入是空的就毫无意义。

### 第五轮结论

**方案的可靠性瓶颈不在归因，在分类。**

归因被严格约束（准确率 35%、必须人确认），但分类器被当作可靠的自动化步骤。而实测证明分类器有三个可复现的误判路径。

**修正建议**：
1. 分类器输出 `unknown` 而非强行二分类
2. `unknown` 默认进入人工队列，而不是丢弃
3. 度量「unknown 率」——如果持续偏高，说明分类规则失效

## 第六轮：这些缺陷为什么在设计阶段没被发现？

### 追问：我做了 4 轮审计（可行性/证据/组织/逻辑），为什么没发现分类器的问题？

回看审计的问题设计：

| 审计角度 | 问的问题 | 是否触及分类器 |
|---|---|---|
| 可行性 | 脚本能跑吗？字段够吗？ | ❌ |
| 证据质量 | 引用的数字对吗？ | ❌ |
| 组织流程 | 人会配合吗？度量会被滥用吗？ | ❌ |
| 逻辑漏洞 | 文档自相矛盾吗？ | ❌ |

**没有一路问「这个机制在什么输入下会给出错误答案」。**

审计都在检查**"文档写得对不对"**，而不是**"机制在真实输入下的行为"**。

### 更深的原因

分类器的错误只有**构造反例输入**才能暴露。而我在设计时用的是**"正常路径"的思维**：

> "重跑不一致 → flaky" —— 这在大部分情况下对

但**"大部分情况对"是一个危险的正确性标准**。在安全关键路径上，99% 正确等于 1% 灾难。

### 第六轮结论

**方案的验证方式有结构性缺陷**：全部验证都是"正向验证"（能跑、数据对、文档一致），没有"对抗验证"（构造让它出错的输入）。

本轮的所有发现（第一到第五轮）都来自**构造反例**，而不是重读文档。

## 第七轮：所以方案的根本问题是什么？

### 汇总前面六轮

| 轮次 | 发现 | 性质 |
|---|---|---|
| 1 | 保护力只来自变异+账本 | 认知修正 |
| 2 | 变异闸门门槛太低（>0） | 设计缺陷 |
| 3 | 37.5% 不可解释（分母含等价变异） | 度量缺陷 |
| 4 | 分类器混淆 flaky 与间歇性 bug | **逻辑缺陷** |
| 5 | 分类误判级联导致归因失效 | **结构性缺陷** |
| 6 | 验证方式只有正向，缺对抗 | 方法论缺陷 |

### 根本问题

**方案假设了"每个环节的判定是可靠的"，并把可靠性建立在"看起来合理"上，而不是"对抗测试"上。**

具体表现：

| 假设 | 现实 |
|---|---|
| 分类器能区分 flaky 与真实 bug | 不能（实测 3 个反例） |
| 杀死数 > 0 说明测试有效 | 只能说明有一条有效 |
| 37.5% 杀死率说明覆盖不足 | 分母不可解释，结论无效 |
| 四路审计能发现设计缺陷 | 只能发现文档缺陷 |

### 第七轮结论

**方案不是"有 bug"，而是"验证方法本身不产生信心"。**

补上 `unknown` 类别、提高变异门槛、修正分母——这些都只是修 symptom。真正的修法是：

> **每个自动化判定都必须有"它会在什么输入下出错"的对抗测试。**

---

## 第八轮：如果重做，应该怎么验证？

### 追问：什么样的验证能防止第六轮的问题？

对比两种验证：

| 类型 | 做法 | 能发现什么 |
|---|---|---|
| 正向验证 | 用正常输入跑，看结果对不对 | 实现错误 |
| **对抗验证** | **构造"应该被判 A，但可能被判 B"的输入** | **判定逻辑错误** |

对抗验证的模板：

```
对每个自动化判定，问三个问题：
1. 它最可能把 A 误判成 B 的具体输入是什么？
2. 这个误判的后果是什么？（丢弃/掩盖/放行）
3. 如果误判发生，有人会知道吗？
```

用这个模板重测分类器：

| 判定 | 误判输入 | 后果 | 有人知道吗 |
|---|---|---|---|
| flaky | 间歇性真实 bug | 不进入归因 | **否** ← 最危险 |
| environment | 断言环境错误值 | 不计入质量指标 | 否 |
| real | — | 进入归因（安全方向） | — |

**只有第三个误判是安全的**（多查一次），前两个都是静默丢失。

### 第八轮结论

**对抗验证的核心指标：误判是否静默。**

任何"把问题归类为可忽略"的判定，都必须有**可见的审计痕迹**，否则误判等于删除。

## 九点五、修正已实施（不只是建议）

四轮递进分析得出的结构性缺陷已经修复并实测：

| # | 修正 | 实测结果 |
|---|---|---|
| 1 | 分类器加入 `unknown` | 3 个反例全部转为 `unknown`，不再被静默排除 |
| 2 | `unknown` 进入人工队列并计入报告 | 报告显示「1 failure(s) could not be classified」，且触发 `ship_with_conditions` |
| 3 | 确认的 flaky 写入 `runs/flake.jsonl` | 第 2 轮运行正确识别为 `flaky`（闭环验证） |
| 4 | 环境判定改为「故障须在 traceback 帧」 | `assert got == 'ConnectionError'` 不再被判环境问题 |

**闭环验证的完整过程**：

```
第 1 轮：test_known_flaky_case 重跑 pass/fail
         → 无 known_flaky 记录 → unknown（正确：证据不足）
         → --record 写入 flake.jsonl
第 2 轮：同样输入
         → 读到 known_flaky → flaky（正确：历史证明）
```

这证明「unknown → 人工确认 → 写入历史 → 后续自动识别」的闭环是成立的。

**仍未修的两项**（需要更多设计，不是代码改动）：

| # | 问题 | 为什么暂不修 |
|---|---|---|
| 5 | 变异杀死率分母未排除等价变异 | 需要人工判定哪些变异等价，无法自动化 |
| 6 | 变异闸门 `> 0` 门槛过低 | 需要先建立模块级基线，是流程问题 |

## 十、这份分析本身的局限

| 局限 | 说明 |
|---|---|
| 只测了分类器 | 闸门、账本、查重未做同等的对抗测试 |
| 未测 AI 生成 | 子会话不可用，AI 生成测试的有效性仍未验证 |
| 变异分类未量化 | 30% 等价变异是假设，未实测 |
| 九轮分析仍是"我想得到的对抗测试" | 无法排除还有没想到的误判路径 |

**最后一条最值得警惕**：这九轮分析本身也是"我构造的反例"。真正可靠的做法是让第二个人构造——因为每个人的盲区不同。
