# AI 测试工作流 · 完整方案 v8

**形态**：可移植 Skill 包（`~/.agents/skills/test-workflow/`）
**适用**：测试组当前「需求来了直接写用例」的现状
**依据**：ISTQB CTFL v4.0 §1.4、ISO/IEC/IEEE 29119-2:2021

**数据时效**：文中仓库统计（测试文件数、断言数）为撰写时快照；当前实测 275 个测试文件、8483 处 assert。

**状态**：可执行。两个关键前提已确认（见 §0.1）。

## 0. 一句话主张

> **AI 不会让测试变好，只会让「测试写了什么」变快。**
> 所以这套方案的重心不是让 AI 多写用例，而是三件事：
> ① 在写之前问清楚需求（可测性评审） ② 写之后用机械闸过滤 ③ 入库之后不让覆盖静默流失。

---

## 0.1 已确认的前提（决定方案可行性）

| 前提 | 确认结果 | 对方案的影响 |
|---|---|---|
| 需求方会配合回答可测性评审的问题 | **会** | 消除最大失败模式（§15.1 第 1 条：评审流于形式） |
| 度量不会被用于个人考核 | **不会** | 度量体系可保持原设计，无需重设计 |

**这两个前提是方案成立的基础，不是细节。**

如果任一前提在未来变化，需要重新评估：

| 前提变化 | 应对 |
|---|---|
| 需求方开始不配合 | 把问题升级给测试负责人，由组织解决；技术上可退化为「记录假设 + 标注未覆盖」，但效果大幅下降 |
| 度量被引入考核 | **立即停止使用该指标**——被考核的指标会立刻失真（§8.1） |

### 0.2 由前提确认带来的设计收敛

既然需求方会配合，「可测性评审」可以从「记录假设为主」升级为「**以获取答复为主**」：

| 环节 | 原设计（需求方不配合） | 收敛后（需求方配合） |
|---|---|---|
| 可测性评审产出 | 三段式清单，重点在「我们暂时假设」 | 三段式清单，重点在「需要明确」并**跟踪关闭率** |
| 阻塞项处理 | 记录假设继续 | **等待答复**，因为阻塞项不答复会设计出错误用例 |
| 度量 | 只看用例重写率 | 增加「**问题回复率**」作为健康度指标 |

因此新增一个度量（见 §8.2）。

## 1. 问题定义

### 1.1 当前流程与它的代价

**现状**：需求 → 直接写用例 → 跑 → 提单。

| 缺失环节 | 后果 |
|---|---|
| 无测试计划/风险登记 | 资源按感觉分配，高风险区可能测得少 |
| **无测试分析** | **不知道漏了什么——这是最致命的** |
| 无设计技术约束 | 只测 happy path，边界值缺失 |
| 无实现验证记录 | 环境问题被误判为代码缺陷 |
| 无完成复盘 | 同样的坑反复踩 |

### 1.2 数据支撑

**缺陷发现越晚，修复成本越高**（归一化到需求阶段 = 1）：

| 来源 | 需求 | 设计 | 编码 | 测试 | 运维 |
|---|---|---|---|---|---|
| Boehm 1981 | 1 | 5 | 10 | 50 | 100+ |
| Hoffman 2001 | 1 | 3 | 5 | 37 | — |
| Rothman 2002 | 1 | 20 | 45 | 250 | — |
| Pavlina 2003 | 1 | 10 | 100 | 1000 | — |
| NASA IV&V（方法3） | 1 | 4 | 7 | 157–186 | — |
| **中位数** | **1** | **5** | **10** | **50.5** | ~100 |

**缺陷来源**：

| 来源 | 结论 |
|---|---|
| Young 2001 | **85% 缺陷源于需求**：错误假设 49%、遗漏需求 29%、不一致 13% |
| Defense AT&L 2014 | ~40% 缺陷产生于需求阶段（设计 10%、编码 45%、测试 5%） |
| Lutz 1993 (NASA) | 安全相关缺陷 48-67% 源于接口规格误解，2/3 是需求问题 |
| 综述 | 50-85% 终身缺陷可追溯到需求错误 |

**结论：最大的风险不是「用例写得少」，而是「写的是错的用例」——而且没人知道。**

### 1.3 AI 放大了这个问题

人工时代，测试员写用例时会在脑中产生疑问并追问需求方。**追问没留记录，但它发生了。**

| 需求「导出报表」未说格式 | 人工 | AI |
|---|---|---|
| 格式 | 问「CSV 还是 Excel？」 | 生成 `test_export_csv()`，**默默假设 CSV** |
| 空报表 | 会问 | 只测有数据，**空报表不测** |
| 权限 | 会问 | **假设所有人都有权限** |

**结果：用例数增加，覆盖的假设面反而缩小。**

这不是 AI 的缺陷，是 AI 的高效填补了空白——**而空白本该被追问**。

## 2. 总体设计

### 2.1 三个环节的自信心差异（核心判断）

| 环节 | 客观验证手段 | 实测可信度 | 设计策略 |
|---|---|---|---|
| 回归（选测试/分类失败） | 跑完就知道 | **高** | 可自动化 |
| 用例生成 | 编译/连跑/变异杀死 | 中 | 机械闸 + 人工评审 |
| 缺陷归因 | 只能靠人确认 | **低（35%）** | 只做建议，绝不自动提单 |

### 2.2 主流程（适配「直接写用例」的现状）

```
需求（外部规划系统 / 口头 / 文档）
   │
   ▼ 阶段 0：可测性评审  ← 唯一能发现「漏测」的环节
   │   产出三段式清单：
   │   · 需要明确（阻塞设计）
   │   · 需要确认（影响范围）
   │   · 我们暂时假设（若不符请告知）
   │
   ├─ strict/guided → ★人工确认（必停）
   └─ auto_ai      → AI 自评 + 落盘留痕
   │
   ▼ 阶段 0.5：查重（case_index.py find）
   ├─ ≥0.85 → 不新建，参数化扩展
   ├─ 0.6-0.85 → 标注关联
   └─ <0.6 → 正常生成
   │
   ▼ 阶段 0.6：冲突检查
   └─ 发现断言冲突 → ★人工裁决（任何档位）
   │
   ▼ 阶段 1：TestIntent（给定X / 调用Y / 断言Z）
   │
   ▼ 阶段 2：生成 + 机械闸（闸1 编译 / 闸2 连跑N次 / 闸3 增量）
   ├─ 任一失败 → 丢弃（记录供误丢率审计）
   │
   ▼ 阶段 3：入库决定
   │   写入 cases/*.yaml（含 contract.statement）
   ├─ strict → ★人工审批
   └─ guided/auto_ai → AI 决定 + 留痕
   │
   ▼ 阶段 4：回归执行 + 失败三分类
   │   （环境 / flaky / 测试缺陷 / 真失败）
   │
   ▼ 阶段 5：归因建议（仅真失败）
   ├─ 证据链 + 置信度
   ├─ strict/guided → ★人工采纳
   └─ auto_ai → 留痕建议
   │
   ▼ 缺陷单（★ 任何档位都由人提）

横切：阶段 6 监控（覆盖账本持续记录）
      阶段 7 完成（里程碑归档 + 教训回流）
```

### 2.3 全局 vs 局部

判据：**是否需要机器高频写入 + 是否跨会话/跨项目存活**。

| 资产 | 层 | 载体 | 所有者 |
|---|---|---|---|
| 测试红线 | 全局 org | 知识条目 `redline` | 组织级 QA |
| flake 注册表 | 全局 | 独立数据 | **CI/环境团队**（非 QA） |
| 测试策略/教训 | 全局 | 知识条目 `convention`/`lesson` | 对应层负责人 |
| 选择策略阈值 | 全局 | 配置 | 平台团队 |
| 测试代码/fixture | 局部 | 用户仓库 `tests/` | 项目负责人 |
| 用例元数据 | 局部 | 工具目录 `cases/*.yaml` | 项目负责人 |
| 运行证据 | 局部会话级 | 会话产物 | 会话所有者 |

**反直觉推论：flake 注册表必须全局**——Google 数据 84% 的 pass→fail 涉及 flake；各项目各自为战则样本不够。

**同时**：flake 治理责任在 CI/环境团队。算在个人头上等于为别人的环境惩罚测试员。

## 3. 用例资产化（方案核心）

### 3.1 身份 = 契约，不是文件

```yaml
case_id: tc-export-csv-001
revision: 3
contract:                                    # 身份：只在需求变时变
  statement: "有 report:read 权限的用户可导出 CSV，且导出被审计"
  requirement_ref: "docs/req/report.md#3.1"
  stability: stable
implementation:                              # 实现：可随代码变
  path: tests/test_export.py::test_csv_export
  framework: pytest
lifecycle:
  state: active
  owner: "报表组"
  importance: critical
```

**契约写不出来 → 说明意图还太虚，回到阶段 1。**

### 3.2 契约变了 vs 实现变了

| 需求 | 实现 | 失败原因 | 处置 | 覆盖变化 |
|---|---|---|---|---|
| 未变 | 变了 | 断言绑定旧实现 | 改实现层 | 不变 |
| 变了 | 变了 | 行为确实变了 | **re-baseline（人确认）** | 显式记录 |
| 未变 | 未变 | flaky/环境 | 分类处理 | 不变 |
| 变了 | 未变 | 需求变了实现没跟上 | **真 bug** | 不变 |

### 3.3 三种静默修改禁止

| 操作 | 后果 | 替代 |
|---|---|---|
| 删除失败用例 | 覆盖缺口无记录 | `retired` + 理由 + 影响分析 |
| 直接改断言对齐新行为 | 看似绿色，覆盖范围变了 | `re-baseline` + 人确认 |
| 长期 `@skip` | 变成无人相信的红色噪声 | `stale` + 限期 |

### 3.4 查重（防重复造轮子）

三级匹配：

| 级别 | 方法 | 成本 |
|---|---|---|
| L1 | 需求锚点（同 `requirement_ref`） | 零 |
| L2 | 契约关键词（**中文字符二元组** + 英文词） | 低 |
| L3 | difflib 模糊 | 中 |

| 相似度 | 处置 |
|---|---|
| ≥ 0.85 | 不新建，参数化扩展 |
| 0.60-0.85 | 标注 `extends:`，评审重点看 |
| < 0.60 | 正常生成 |

**阈值偏保守是刻意的不对称设计**：
- 假阴性（真重复算低分）→ 多写一条重复测试，可接受
- 假阳性（不同算高分）→ **压掉真正需要的用例**，不可接受

**参数化优先于新建**（实测差异巨大：低参数化模型 12.7%，高参数化 91.8% —— arXiv 2504.18985）。

### 3.5 冲突处理

| 冲突类型 | 检测 | 处置 |
|---|---|---|
| 断言冲突（旧 404 / 新 200） | **人工裁决**（自动检测不可实现） | `supersede` / `coexist` / `reject_new` |
| 契约冲突 | 需求引用比对 | 同上 |
| 数据冲突 | fixture 依赖分析（L3 兜底） | 同上 |

**任何档位都需要人裁决**——这是「决定放弃什么覆盖」。

### 3.6 生命周期

```
generated → gated → [审批] → active ──→ retired
                    │          │
                    │          ├──→ stale ──→ {repaired | re-baselined | retired}
                    └ rejected └────────┘
```

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| `active` | 审批通过 | 失败无法修复 / 需求变更 |
| `stale` | 同 revision 连续 2 次失败（自动） | 修复 / re-baseline / 退役 |
| `re-baselined` | **人确认 + 需求变更出处** | 下轮通过 → active |
| `retired` | **人确认 + 理由** | 无（可恢复） |

```
stale > 14 天 → 通知 owner
stale > 30 天 → 自动 retired
```

**已知风险（未防护）**：因未修复真实 bug 而失败的用例，30 天后被自动退役 → bug 证据消失。需确认是否豁免「关联未关闭缺陷」的用例。

### 3.7 覆盖账本（关键产出）

```json
{"case_id":"tc-export-csv-001","change":"retired",
 "from_contract":"导出必须被审计",
 "requirement_change_ref":"docs/req/report.md#3.1-v2",
 "authorized_by":"张三","importance":"critical","net_coverage_delta":-5}
```

回归报告必须显示：

```
覆盖账本（近 30 天）：net weighted delta: -5
  - tc-export-csv-001 retired [critical] ref=docs/req/report.md#3.1-v2 by=张三
[WARN] net coverage is shrinking. Confirm each removal is an intended requirement change.
```

**为什么用权重**：一条契约可能是 `1+1=2`，也可能是「支付不能重复扣款」。单看「-2 契约」对管理者无意义。权重（critical=5 / high=3 / normal=1 / low=0.5）。

**强制授权**：`retired`/`re-baselined`/`superseded` 必须提供授权人 + 理由，后两者还需需求变更出处。缺任一项工具拒绝写入。

## 4. 分层测试（空间维度）

### 4.1 五层与它们的本质差异

| 层次 | 单次耗时 | flake 率 | 变异可行 | 主指标 | 数量控制 |
|---|---|---|---|---|---|
| L1 单元 | ms | 0.5%（Google small） | ✅ | 变异杀死率 | 不限 |
| L2 接口 | 10-100ms | 低 | ⚠️ 需重启服务 | 契约矩阵 | 不限 |
| L3 组件 | 10-100ms | 低-中 | ⚠️ JS 工具不成熟 | 状态矩阵 | 不限 |
| L4 页面 | 1-10s | **14%（Google large）** | ❌ | flake 率 | ≤50 |
| L5 集成 | 10s+ | 高 | ❌ | 流程通过率 | ≤10 |

### 4.2 闸门矩阵（**权威版本，覆盖此前所有冲突**）

| | 闸1 编译 | 闸2 连跑 | 闸3 增量 |
|---|---|---|---|
| L1 单元 | 必需 | **3 次** | 变异（杀死>0） |
| L2 接口 | 必需 | **5 次** | 契约矩阵 |
| L3 组件 | 必需+TS | **5 次** | 状态矩阵 |
| L4 页面 | 必需 | **10 次** | 路径唯一性 |
| L5 集成 | 必需 | **1 次** | 无 |

**说明**：早期文档写「统一 5 次」是简化，本表为准。理由：flake 率随层升高（L4 取 10 次因 Google large=14%）；L5 因成本改为「失败重跑 1 次」。

### 4.3 职责边界

| 层次 | 应测 | 不应测（下放） |
|---|---|---|
| L1 | 分支、边界、错误处理 | DB、网络、真实 FS |
| L2 | 参数校验、状态码、权限、幂等 | 业务规则每个分支（L1 的活） |
| L3 | 渲染、交互、加载/错误态 | 后端逻辑、真实网络 |
| L4 | 用户目标可达 | 字段边界穷举（L1/L2 已覆盖） |
| L5 | 跨系统连通、一致性 | 单点功能细节 |

**核心原则：选能验证契约的最低层。**

**反模式**：E2E 里穷举字段校验、单元测试连真数据库、页面测试断言 API 调用次数。

### 4.4 层间覆盖原则

```
L1 覆盖分支逻辑 100%
L2 覆盖端点契约面（每个参数组合、每个错误码）
L3 覆盖组件状态组合（loading/error/empty/normal）
L4 只覆盖「用户目标可达」，不复查 L1-L3
L5 只覆盖「跨系统连通与一致性」
```

判据：**上层断言「整体能否用」，下层断言「零件是否正确」。**

### 4.5 E2E 预算与准入

```yaml
e2e:
  max_cases: 50
  max_total_seconds: 600
  per_case_seconds: 90
  stability_runs: 10
  parallelism: 1        # 仓库现状；提升需先解决数据隔离
```

**新增 E2E 必须满足至少两条**：
```
□ 完整用户目标（不是功能点）
□ 跨越 L1-L3 无法模拟的边界
□ 关键业务（支付/登录/导出）
□ 曾出线上事故需防回归
```

**E2E 失败处理**：先重跑 → 通过则 flaky；仍失败 → **先看对应 L2/L3 是否也失败** → 都通过才可能是真实集成问题。

**E2E 失败绝不直接归因产品代码。**

## 5. 环节流程（时间维度）

### 5.1 七环节与现状的差距

| 环节 | 现状 | 本方案要求 | 依据 |
|---|---|---|---|
| 1 Planning | 无 | **可选**（小团队靠经验） | 价值在资源协调 |
| 2 Monitoring | 无 | **轻量推荐**（覆盖账本） | 纯数据，成本极低 |
| **3 Analysis** | **无** | **必须补**（可测性评审） | 40-85% 缺陷源于此 |
| 4 Design | 有（写用例） | **加固**（等价类/边界值/参数化） | 已有基础 |
| 5 Implementation | 有 | 加固（环境验证记录） | 需要证据 |
| 6 Execution | 有 | **加固**（三分类 + 账本） | 缺分类 |
| 7 Completion | 部分 | 轻量（完成报告 + 教训回流） | 关键是回流 |

**只补一个环节，就补 Analysis。**

### 5.2 各环节 AI 边界

| 环节 | AI 价值 | AI 风险 | 人工必需 |
|---|---|---|---|
| 1 Planning | 中 | **高**（风险等级错=资源全错配） | 风险等级、范围 |
| 2 Monitoring | **高**（纯数据） | **低** | 纠偏决策 |
| 3 Analysis | **极高**（语义提取） | 高（漏条件=没测） | **条件确认、优先级、歧义裁决** |
| 4 Design | **极高**（批量生成） | 中 | 技术选择 |
| 5 Implementation | 高 | 中 | 环境验证 |
| 6 Execution | 高 | **高**（归因 35%） | **分类抽查、提单** |
| 7 Completion | 中 | 低 | 教训提炼 |

### 5.3 环节 3 的详细要求（可测性评审）

八类系统性检查：

1. **可判定性**（「响应要及时」→ 追问量化）
2. **输入边界**（空值/极值/超长/特殊字符）
3. **状态与顺序**（重复/乱序/并发/中断）
4. **权限与隔离**（最常漏，最常致事故）
5. **异常与失败**（依赖失败/超时/部分成功/重试）
6. **数据一致性**（事务/回滚/最终一致）
7. **自相矛盾**（需求内部冲突）
8. **隐含假设**（已登录/数据已存在）

**产出三段式清单，可直接发需求方**：

```markdown
### 一、需要明确（阻塞设计）
1. 「导出」格式：CSV / Excel / PDF？
2. 导出全部数据还是筛选结果？

### 二、需要确认（影响范围）
3. 谁有权限导出？跨租户隔离吗？
4. 需求 3.1 说「必须审计」，3.5 说「可选」，以哪个为准？

### 三、我们暂时假设（若不符请告知）
- 假设用户已登录且有 report:read 权限
```

**验收判据：如果评审后用例和评审前一模一样，说明白做了。**

### 5.4 环节 6 的失败三分类

顺序不可颠倒：

```
1. 环境问题？   → environment（不计入测试质量指标）
2. flaky？      → flaky（不进入归因）
3. 测试缺陷？   → test_defect
4. 都不是       → real（进入归因）
```

**报告必须分离信号与噪音**：

```
不要：42 个测试，3 个失败
要说：42 个测试：20 通过，22 失败。
      只有 3 个是真实问题；另外 19 个是噪音（12 环境、5 flaky、2 测试写错）。
```

### 5.5 测试报告（环节 7 的产出物）

跑完测试必须产出报告。没有报告等于「跑完了但没人知道能不能发」。

**报告第一段是结论，不是通过率。** 依据 IEEE 829-1998 §11 与 ISO/IEC/IEEE 29119-3:2021 §7.4。

> "A pass rate without context is noise. 95% pass rate could mean 5 tests failed out of 100, all cosmetic. Or it could mean 50 tests failed out of 1,000, including payment flow."

三种结论与 CI 退出码：

| 结论 | 退出码 | 触发条件 |
|---|---|---|
| `ship` | 0 | 所有闸门通过，无未缓解风险 |
| `ship_with_conditions` | 1 | 有 high 缺陷待跟踪，或高风险用例缺需求锚点 |
| `hold` | 2 | critical 缺陷未修复、覆盖无解释收缩、**或根本没有任何测试证据** |

**关键设计：没有测试数据时必须 `hold`**。空状态返回 `ship` 是危险假阳性——什么都没跑不等于没问题（实测中正是先犯了这个错误才修）。

报告八段（**顺序是读取顺序，不是标准顺序**）：

| # | 段落 | 标准依据 |
|---|---|---|
| 1 | 结论 | IEEE Evaluation 提前 |
| 2 | 范围与覆盖（含**没测什么**） | IEEE Comprehensiveness |
| 3 | 结果（按层表格） | 实践 |
| 4 | 失败与残余风险 | ISO 29119-3 Residual risks |
| 5 | 覆盖账本 | **本方案特有** |
| 6 | 偏差与阻碍 | ISO 29119-3 Factors that blocked progress |
| 7 | 依据（文件链接，不贴日志） | 实践 |
| 8 | 批准 | IEEE Approvals |

**为什么不照抄标准顺序**：IEEE 829 把 Evaluation 放第 6 段（从事实到结论），符合文档规范但违反阅读习惯。决策者需要 3 秒内知道结论。本设计首尾都给结论：开头是判断，结尾是依据。

**刻意不包含的指标**（都是虚荣指标）：

| 不包含 | 原因 |
|---|---|
| 总测试数 | "Twelve hundred tests executed tells you team was busy. It doesn't tell you whether payment flow works." |
| 自动化率 | 与质量无关 |
| 通过率（作为首段） | 脱离上下文无意义 |
| 执行耗时 | 除非超预算 |
| 每个用例明细 | 属于附录 |

判据：**报告里每一个数字都必须能改变一个决策。**

### 5.6 环节 7 的关键：教训回流

```
lessons learned → 必须回流到风险登记表
```

**如果复盘不回流，下一轮还会犯同样的错。**

## 6. 人工介入设计

### 6.1 三档 review_mode

| 档位 | 停在哪 | 适用 |
|---|---|---|
| `strict` | 阶段 0、3、5 全停 | 合规、高风险 |
| `guided`（默认） | **只停阶段 0（可测性评审）** | 大多数团队 |
| `auto_ai` | 从不停（强制留痕） | 个人项目、夜间批处理 |

### 6.2 为什么默认 guided

**可测性评审/意图确认不可委托给 AI——这是能力盲区，不是能力不足。**

机械闸验证「实现对不对」，测不了「测的是不是那个东西」。AI 无法判断自己的理解是否符合需求语义。

而入库和归因有客观信号兜底（变异增量、置信度 + 证据链）。

### 6.3 任何档位都需要人的四件事

| 事项 | 为什么 | 由谁做 |
|---|---|---|
| **风险等级**（若做 Planning） | 决定全部资源分配 | 测试负责人 |
| **断言冲突裁决** | 同一行为两种期望，必有一条错 | 该层测试负责人 |
| **删除/修改已入库用例** | 覆盖流失点 | 用例 owner + 授权人 |
| **缺陷单** | 归因准确率仅 35% | QA 分析师 |

共同点：本质都是**「决定放弃什么」**，价值判断无法从代码推导。

**注意这四件事与 review_mode 无关**。`auto_ai` 也不豁免——因为它们的对象不是「AI 的产出质量」，而是「组织的风险承担」。

### 6.3.1 与 §6.1「guided 只停一处」的表面矛盾

§6.1 说 `guided` 只停阶段 0，但 §6.3 说任何档位都要人做四件事。这不是矛盾，是**两类不同的介入**：

| 类型 | 频率 | 性质 |
|---|---|---|
| **流程停顿**（§6.1 的三档） | 每个需求/每个用例 | 常规把关 |
| **例外裁决**（§6.3 的四件事） | 仅在发生时 | 异常处理 |

换句话说：`guided` 意味着「正常流程不打断人」，不代表「异常情况也自动决定」。冲突、删除用例、提缺陷单本来就是低频事件，因此让人介入的成本可以接受。

### 6.4 auto_ai 的强制防护

| 防护 | 说明 |
|---|---|
| 记录模式 | `mode: auto_ai` + `decided_by: ai` |
| 抽样审计 | 每周抽 N 条（优先低置信度），第二位评审人独立判断，统计偏差率 |
| 组合校验 | `auto_ai` + 无变异测试 → **拒绝**（已实测生效） |
| 偏差率熔断 | > 25% → 建议关闭 |

### 6.5 审核记录（文件化）

```yaml
target_kind: test_case
target_id: tc-abc123
target_revision: 2            # 内容变则审批作废
decision: approved
mode: guided
decided_by: ai
reason: "闸3 杀死 3 个变异体"
gate_results: {compile: passed, stable: passed, mutation_delta: 3}
ai_confidence: medium
audit_status: unaudited
```

**reviewer 是自由文本**（企业用 SSO 用户名，个人用 git 用户名）——避免要求宿主提供用户体系。

**代价**：无权限校验（信任环境）；批量审批靠脚本（适合 20-50 条/周）。

### 7.4.1 实测中发现的工具约束（必须写进配置）

**变异测试工具在 Windows 上只能用 cosmic-ray，不能用 mutmut。**

| 工具 | Windows 原生 | 实测结论 |
|---|---|---|
| mutmut 3.x | ❌ 拒绝运行 | 报错 `To run mutmut on Windows, please use the WSL` |
| cosmic-ray | ✅ 可用 | 三阶段（init → exec → dump），需注意 4 个坑 |

**cosmic-ray 的四个坑（已在 gate_check.py 中处理）**：

| 坑 | 症状 | 处理 |
|---|---|---|
| TOML 文件带 BOM | `invalid character in key name: ']'` | 以 `utf-8` 无 BOM + `newline="\n"` 写入 |
| Windows 路径含反斜杠 | `Reserved escape sequence used` | 命令行中的 `\` 全部转成正斜杠 |
| `module-path` 给成导入名 | `Could not find module path core.x.y` | 必须传**文件路径**（`core/x/y.py`） |
| `test-command` 写成子表 | 每个变体 `incompetent`（`'ConfigDict' object has no attribute 'read'`） | 必须在 `[cosmic-ray]` 段内写成**字符串** |

**实测成本**：`core/team_context/integrations.py`（约 100 行）跑一次完整变异测试 **约 10 分钟**，产生 195 个变体、杀死 72 个。这印证了方案 §4.2 的判断——**变异测试只适合 L1 单元层**。

### 7.4.2 实测中修复的逻辑缺陷

**`triage_failures.py` 的 `--rerun-outcomes` 曾应用于所有失败项**：

原实现把一次重跑观测套用到整批失败上，导致一个 flaky 结果会把真实 bug 也伪装成 flaky。实测中「test_real_bug」被判成 flaky。

修复：改为按测试独立提供（`--rerun-for '{"test::name": "pass,fail,pass"}'`），单测试场景仍可用 `--rerun-outcomes`。修复后分类正确（环境 1 / flaky 1 / 真实 1）。

### 7.5 脚本与方案的关系（边界）

脚本是可替换的实现，方案是不可替换的规则：

| 层 | 内容 | 可替换性 |
|---|---|---|
| **规则**（方案） | 闸门必须按层配置、失败必须三分类、覆盖变更必须记录授权 | 不可替换 |
| **实现**（脚本） | 具体用什么命令跑闸门、从哪种 XML 读结果 | 可替换 |

因此脚本的配置项（`runners`）刻意做成声明式：

```yaml
runners:
  unit:
    command: ["{python}", "-m", "pytest", "{target}", "-q"]
```

换框架只改配置，不改脚本。`{python}` 占位符解析为当前解释器，避免 venv 不在 PATH 的常见问题（实测中首次运行就遇到了这个问题）。

## 8. 度量体系

### 8.1 硬规则

**以下指标禁止用于个人考核。任何用它们做个人排名的行为，视为度量失效并作废。**

理由：分子分母都可由被考核者操纵（压低标准提高接受率、skip 而非删除提高存活率）。一旦进入考核，测的是表演。

### 8.2 指标（按层与环节）

| 指标 | 定义 | 健康阈值 | 归属环节 |
|---|---|---|---|
| 契约覆盖率 | active 用例数 / 可测试点数 | >80% | Analysis |
| **净覆盖变化** | 30 天账本加权净和 | **≥0** | Monitoring |
| **需求问题回复率** | 已答复的阻塞项 / 提出的阻塞项 | **>80%** | Analysis |
| **阻塞项平均关闭时长** | 从提出到答复的中位天数 | **<3 天** | Analysis |
| 重复率 | 相似>0.85 的用例对 / 总数 | <5% | Design |
| 腐化率 | `stale` 占比 | <10% | Execution |
| AI 与人偏差率 | 抽样中被推翻的比例 | <10% | Completion |
| 误丢率 | 被闸门丢弃但实际有效 | <10% | Design |

**「需求问题回复率」是新增的关键指标**（因需求方已确认会配合）。它直接反映可测性评审是否真的在起作用：

- 回复率 > 80% → 评审有效，需求方在参与
- 回复率 50-80% → 部分问题被忽略，需检查提问质量（是否问得太琐碎）
- 回复率 < 50% → 要么问题质量差，要么需求方开始不配合 → **触发 §0.1 的前提复核**

### 8.3 不采用的指标

| 指标 | 原因 |
|---|---|
| 生成用例数 | 激励刷量（Meta：75% 编译里只 1/3 有用） |
| AI 参与率 | 与价值无关 |
| 自报接受率 | 分子取决于评审人心情，而评审人是被考核者 |
| 用例总数 | 可通过不退役虚增 |
| 3 个月存活率 | 与「自动标记失效」激励相反；skip 能绕过 |
| **行覆盖率（L4/L5）** | **无意义**：一个 E2E 能覆盖几千行但不验证任何行为 |

## 9. 验证方法

### 9.1 最高风险假设

**生成的测试「通过但无效」**——能编译、能稳定通过的测试可能只在复述实现。

### 9.2 证伪实验（已验证，见 §9.6）

取历史「修复真实 bug」的 commit：
1. `git checkout <commit>^ -- <affected files>` 把代码恢复到修复前
2. 跑测试，看哪些失败（失败 = 抓住了该缺陷）
3. `git checkout HEAD -- <files>` 恢复

| 结果 | 结论 |
|---|---|
| ≥60% 失败 | 方向成立 |
| 40-60% | 灰区，扩样本 |
| <40% | 不成立 |

**统计依据**：n=20 的置信区间约 ±22%，所以 60% 与 30% 不可区分。

**⚠️ 禁止用 `git stash` 回退**：`git stash` 恢复的是 HEAD 版本。若被测修复已在 HEAD 中，实验条件根本没建立，会得出「测试无效」的**假阴性**——这个错误会让人错误地放弃一个有效方案。（实测中犯过，详见 §9.6.1）

### 9.3 不能证明什么（必须诚实说明）

1. 只证明抓**历史** bug，不证明抓未来 bug
2. 可能被训练数据污染（应挑训练截止日后的 commit）
3. 不证明组织能吸收 4 倍候选量

### 9.4 不需要任何基础设施

只需 git 历史 + 一次 API 调用。

### 9.5 变异测试：验证「测试是否有效」的唯一手段

**证伪实验验证「测试能否抓住缺陷」，变异测试验证「测试是否足够严格」——两者不可互相替代。**

做法：向源码注入人为缺陷（变异），看测试是否失败。

| 变异结果 | 含义 |
|---|---|
| 测试失败（killed） | 该测试能检测这类缺陷 |
| 测试仍通过（survived） | 该测试对这类缺陷不敏感 |

**为什么覆盖率不行**：覆盖率只看「这行代码被执行了」，不看「执行结果被验证了」。实测证据（§9.6.3）：去掉 `fsync` 后代码行照常执行、覆盖率不变，但持久化保证已经消失。

**等价变异（equivalent mutant）**：某些变异不改变程序行为，任何测试都杀不死。这**不是测试缺陷**。例：`os.open(..., 0o600)` 之后又 `chmod(0o600)`，去掉 chmod 结果相同。

### 9.6 实测结果（2026-11-18/19）

#### 9.6.1 证伪实验：补写的测试能否抓住真实缺陷

对 `15e7ec22`（Jenkins/K8s 安全加固，5 处修复）做实验：

| 条件 | 结果 |
|---|---|
| 修复前代码 + 11 个新测试 | **5 failed, 6 passed** |
| 修复后代码 + 同样测试 | **11 passed** |

失败的 5 个逐一对应 5 个修复点（`_pick` 静默回退、路径未转义、`..` 处理、tokenFile 错误、crumb 崩溃）。

**结论：补写的测试具备真实回归保护能力，不是「通过但无效」。**

**方法论错误记录**：首次实验用 `git stash` 回退，得到「测试抓不住」的错误结论。原因是 stash 恢复 HEAD 版本，而修复已在 HEAD 中——实验条件未建立。改用 `git checkout <commit>^ -- <files>` 后得到正确结果。

#### 9.6.2 覆盖空白实证

`15e7ec22` 修复了 5 个**安全**缺陷，当时**零测试覆盖**（`test_integrations.py` 只测配置读写与掩码）。

| 时间点 | 缺陷 | 测试保护 |
|---|---|---|
| 修复前 | 5 个安全缺陷存在 | 0 |
| 修复后（当时） | 已修复 | **仍然 0** |
| 补测后 | 已修复 | 11 个（5 个是真正的守卫） |

**若中途有人重构 `k8s_service.py`，这 5 个缺陷会无声回归。**

#### 9.6.3 变异测试：测试严格度测评

对补写的测试注入 11 个人工变异：

| 结果 | 数量 | 比例 |
|---|---|---|
| KILLED | 10 | **91%** |
| SURVIVED | 1 | 9%（等价变异，合理） |

**测评过程中发现 3 个真实测试缺口**（若不做变异测试永远发现不了）：

| 缺口 | 为什么覆盖率看不出 | 补测方式 |
|---|---|---|
| `fsync` 无人验证 | 去掉后代码照常执行、结果正确 | 断言 `os.fsync` 被调用（过程断言） |
| `hash()` 命名同进程稳定 | 同进程内 `hash()` 稳定，测试抓不住 | **跨进程比对**（`PYTHONHASHSEED` 不同） |
| PEM 权限测试在 Windows 跳过 | 平台条件跳过 → 变异存活 | 断言传给 `os.open` 的 mode（跨平台） |

**核心教训（写进所有生成用例的规范）**：

> **断言「结果正确」抓不住「实现方式」的缺陷。**
> 原子性、持久性、权限窗口这类问题，必须断言**过程**而非**结果**。
> 例：`path.write_text(...)` 与 `os.open→write→fsync→os.replace` 的行覆盖率可以完全相同，但后者才有崩溃保护。

#### 9.6.4 顺带发现的产品缺陷

写测试时发现 `_seg("..")` 返回 `".."` —— `urllib.parse.quote` **不转义点号**，而 `..` 会被 HTTP 客户端规范化掉，路径穿越未被阻止。这是**修复本身有残留缺口**，已补 `%2E`。

**这个缺陷是写测试时发现的，不是读代码时发现的**——「补测试」比「批量生成」更能在早期暴露问题。

### 9.7 执行顺序

```
1. 先做证伪实验（1 天，零基建）—— 判断方向是否成立
2. 再补历史缺陷测试（收益最高）—— 填补已知空白
3. 然后才做新需求的用例生成 —— 有基线才有对比
4. 变异测试贯穿全程 —— 每次补测试后验证严格度
```

**顺序不能颠倒**：先补历史缺陷的收益高于批量生成新测试，因为前者填的是**已经发生过的风险**，后者防的是**可能发生的风险**。

## 11. 无需求文档时的降级模式

**这是现实中最常见的情况：需求来自口头、IM、邮件、或一句话的工单。**

### 11.1 降级策略

| 情况 | 做法 |
|---|---|
| 有结构化需求文档 | 正常走八类检查 |
| 有非结构化需求（IM/邮件/工单） | 先**反向提炼**成结构化需求，再检查 |
| 完全没有需求（只有一句话） | **反向从代码/UI 提炼契约**，然后请人确认 |

### 11.2 反向提炼（当前无需求文档时的唯一可行路径）

```
代码/UI 现状 → 提炼「现有行为」→ 请人确认「这是否是期望行为」→ 确认为契约
```

**关键**：提炼出的是「现在是什么」，不是「应该是什么」。必须人确认。

```yaml
reverse_derived_contract:
  source: "从 tests/test_export.py 与 core/export/report_service.py 提炼"
  observed: "导出返回 200，CSV 含表头"
  confirmed_by: null          # 必须人填
  question: "这是期望行为吗？还是有些是不该有的（bug）？"
```

**这个模式的危险**：可能把 bug 固化成契约。所以**必须人确认**，且标记 `source: reverse_derived`。

## 13. 执行顺序（一次性全量执行，不分期）

本方案不分期、不设里程碑、不做渐进落地。**所有环节按下列顺序一次执行完**。

### 13.1 每个需求的固定动作序列

```
1. 阶段 0：可测性评审（八类检查 → 三段式清单 → 阻塞项获取答复）
2. 阶段 0.5：查重（case_index.py find）
3. 阶段 0.6：冲突检查
4. 阶段 1：TestIntent → 人确认
5. 阶段 2：生成 + 机械闸（闸1/闸2/闸3）
6. 阶段 3：入库决定（写 cases/*.yaml）
7. 阶段 4：回归执行 + 三分类
8. 阶段 5：归因建议（仅真失败）→ 人采纳 → 人提缺陷单
```

### 13.2 配套动作（与上述序列并行，不是先后）

| 动作 | 时机 | 说明 |
|---|---|---|
| 覆盖账本记录 | 每次退役/re-baseline | 追加 JSONL，无需批次 |
| 抽样审计 | 每次 AI 决定后累积 | 达到抽样量即复核 |
| 废弃用例误丢率审计 | 每次被闸门丢弃后累积 | 达到抽样量即复核 |
| 教训回流 | 每次里程碑 | 写入知识条目 |

### 13.3 不做的三件事

| 不做 | 原因 |
|---|---|
| 分期推进（P0/P1/P2） | 方案要求各环节同时生效；只做一半会导致闸门缺失（如只做生成不做覆盖账本，覆盖流失不可见） |
| 试点验证 | 契约、账本、可测性评审互相依赖，试点时缺一环就无法得到真实信号 |
| 等待工具补全后再启用 | 未实现的三个脚本有手工降级路径（§7.4），不阻塞流程 |

## 14. 核心结论

1. **补 Analysis，不补全套七环节**——Planning 的价值可被经验替代，Analysis 的价值不能。

2. **可测性评审是唯一能发现「漏测」的检查**——所有机械闸只能验证「已写的合格与否」。

3. **AI 让这个问题更严重**——它用「合理默认值」填满需求空白，用例数增加但覆盖的假设面缩小。

4. **闸3 只在 L1 用变异测试**——其余层用契约矩阵/状态矩阵/路径唯一性。硬套 E2E 是浪费。

5. **覆盖账本是防流失的唯一手段**——让「-5 契约」在回归报告里可见。

6. **归因只做建议**（35% 准确率），**缺陷单永远人提**。

7. **度量禁止个人考核**——一旦进入，测的是表演不是健康度。

## 15. 方案自身的失效条件（什么情况下这套方案不该用）

**任何方案都有适用边界。以下是明确的「不该用」清单**：

| 条件 | 为什么不该用 | 替代 |
|---|---|---|
| **需求完全不明确且无法追问**（如纯探索性开发） | 可测性评审无从下手；强行做会产出一堆无法回答的问题 | 先做原型/探索测试，稳定后再引入 |
| **产品处于剧烈变动期**（每周大改） | 契约天天变，用例资产化成本高于收益 | 只做 L1 单元 + 冒烟，暂不做契约管理 |
| **团队 < 3 人** | 流程开销（评审、账本、状态机）超过收益 | 只用「选最低层 + 闸门」两条，跳过资产化管理 |
| **已有成熟的测试管理平台且流程稳定** | 与本方案并存意味着两份真相 | 只借鉴「可测性评审」和「覆盖账本」两个概念，嵌入现有平台 |
| **无 CI，靠手工跑测试** | 闸2/闸3 无法自动执行；覆盖账本无法持续累积 | 需具备 CI 才能启用本方案 |
| **测试环境不可重复**（共享且经常被人改） | 闸2 稳定性判定失效；flake 归因不可靠 | 先解决环境隔离 |

**判断方法**：如果上表命中两条以上，**不要推行完整方案**，只取「可测性评审」这一条——它是唯一零依赖、立即能用的部分。

### 15.1 最可能的失败模式

按发生概率排序：

| # | 失败模式 | 早期信号 | 预防 |
|---|---|---|---|
| 1 | 可测性评审流于形式（问的问题需求方不理） | **需求问题回复率 < 50%** | 已确认会配合；若跌破阈值则触发前提复核（§0.1） |
| 2 | 评审耗时过长导致跳过 | 单需求评审 > 40 分钟 | 按需求复杂度分级：简略需求只查 3 类 |
| 3 | 用例元数据无人维护，`contract.statement` 变成空话 | 新用例的契约字段写的是「测试导出功能」 | 契约必须能追溯到 `requirement_ref`，否则不入库 |
| 4 | 覆盖账本没人看 | 净变化持续为负无人过问 | 把净变化放进回归报告，与测试结果同列 |
| 5 | `auto_ai` 偏差率超标但无人关 | 抽样审计的 `sampled_bad` 比例上升 | 偏差率 > 25% 时工具直接拒绝（已实现） |

**第 1 条已被前提确认化解**（需求方会配合），但仍需监控：**「现在会配合」不等于「一直会配合」**。当需求方开始敷衍时，最先体现的就是「需要明确」的问题没人答——这就是为什么 §8.2 把回复率列为指标。

| 需求 | 复用 | 说明 |
|---|---|---|
| 组织归属 | 团队上下文 ownership 链 | 六层模型 |
| 测试红线/策略 | 知识条目（redline/convention/lesson） | 已有类型 |
| CI 日志 | Jenkins/K8s 集成 | 已交付 |
| 定时回归 | automations | 已有 |
| 命令安全 | 参数数组、无 shell、超时、输出截断 | 既有契约 |

**不复用**：

| 不复用 | 原因 |
|---|---|
| 会话产物表 | 会话级 + 级联删除，无法做跨会话资产 |
| 知识条目存用例 | 字段全字符串，无代码/执行历史/flake 率 |
| 宿主审批表 | 覆盖工具调用，不是业务决策，且无决策人字段 |
